# Spike: engine-basics (THROWAWAY)

Timebox: 1 session.

Question: If I knew that DuckDB's Node API (@duckdb/node-api) can (a) enforce read-only
by construction (not by SQL text inspection), (b) produce a data card for a Parquet/CSV
file from parquet_metadata()/parquet_schema()/SUMMARIZE with zero config, and (c) give a
scan-size estimate before execution via EXPLAIN, I would build `core` directly on it.

Observation that answers it:
- (a) a write statement (CREATE/INSERT/COPY TO/ATTACH-write) and external file access fail at the engine
- (b) card (schema, row count, null/min/max/approx distinct) printed from a Parquet + CSV file
- (c) EXPLAIN output exposes an estimated cardinality usable for a cost guard

## Attempts

All probes: @duckdb/node-api (npm, node v22.22.0), in-memory instance. Fixtures: big.parquet
(1,000,000 rows x 3 cols, 8.6 MB, 9 row groups), small.csv (100 rows). Code: probe*.mjs.

### A. Read-only by construction
Tried (probe.mjs): SET allowed_directories=[dir]; enable_external_access=false; lock_configuration=true.
Observed: read inside dir OK; read /etc/hostname -> "Permission Error ... file system operations are
disabled by configuration"; unlock -> "configuration has been locked". BUT `COPY (SELECT 1) TO dir/out.csv`
SUCCEEDED (Count 1, file written) and ATTACH of a new db file inside dir succeeded and created x.duckdb.
Concluded: allowed_directories is read AND write. Not sufficient.

Tried (probe2/3): SET allowed_paths=[exact files] instead, then the same lockdown.
Observed: SELECT from allowed file OK (1000000). COPY TO other path, COPY TO a sibling of an allowed
file, ATTACH other db, and COPY over an allowed file (victim.parquet) all -> Permission Error (DuckDB
writes via tmp_<name>, which is not in the allow-list; victim still 1000000 rows). Locked config can't be reopened.
Concluded: allowed_paths (exact files) + enable_external_access=false + lock_configuration=true blocks
writes by the engine, without inspecting SQL text. Caveat: relies on the temp-file write path being
disallowed; re-check at each DuckDB upgrade (add to security tests).

Tried: DuckDB file opened with access_mode READ_ONLY.
Observed: INSERT / CREATE -> "attached in read-only mode". But `COPY (SELECT 1) TO out3.csv` SUCCEEDED
(file written). Concluded: access_mode READ_ONLY alone does not stop file writes; must be combined with
the allowed_paths lockdown.

Not yet tried: allowed_paths for http/s3 URLs, ATTACH to Postgres (READ_ONLY), how a Source adds paths
before lock (config is locked, so the allow-list must be fixed per instance at open time -> one instance per Source set).

### B. Data card without a full scan
Observed (probe3/4): parquet_schema -> name/physical type/converted type (id INT64, region UTF8,
amount DECIMAL). parquet_file_metadata -> num_rows 1000000, num_row_groups 9. parquet_metadata grouped
-> per-column compressed bytes (id 4.0 MB, amount 4.6 MB, region 19 KB), null_count (amount 142858 =
14.29%, matches SUMMARIZE). Footer queries: 8 ms.
GOTCHA: footer min/max for amount (DECIMAL) came back as mn 1.5 / mx 921598.5, but the true max is
1499997.0 (SUMMARIZE). Footer stats are byte-ordered strings for some types, so min/max from the footer
must not be shown as truth for non-integer types without a note.
SUMMARIZE on the 1M-row file: 225 ms; gives min, max, approx_unique, avg, std, q25/50/75, count,
null_percentage; quantiles and approx_unique are approximate (id approx_unique 962761 vs 1000000 true).
CSV: DESCRIBE SELECT * FROM 'small.csv' infers the type with zero config (i BIGINT).
Concluded: a card of schema + rows + nulls + approximate stats is feasible; "approximate" must be
labeled in the card (principle: say what was not shown).

### C. Cost estimate before running
Observed: EXPLAIN (FORMAT JSON) exposes "Estimated Cardinality" per operator without executing.
For `WHERE amount > 1000` it said 200000; the real count is 856571. The number is a fixed-selectivity
heuristic, not a statistic (it is 1M * 0.2).
Concluded: EXPLAIN is a usable order-of-magnitude guard for scan size (it is exact for the unfiltered
scan, which is where the cost comes from), not a row-count promise. Prefer parquet_metadata bytes for
the "bytes to scan" threshold; use EXPLAIN only for operator shape.

## Answer
Yes, with changes: build core on @duckdb/node-api. Read-only must be enforced with allowed_paths
(exact files) + enable_external_access=false + lock_configuration=true, NOT allowed_directories and NOT
access_mode alone (both let COPY TO write files). Cost guard: bytes from parquet_metadata, cardinality
from EXPLAIN as a rough hint only. Footer min/max not trustworthy for decimals.

copy-pasted lockdown per probe, errors collapsed to the first line, fixtures generated by the probe,
