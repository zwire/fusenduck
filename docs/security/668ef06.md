# Security review: 668ef06

The target is `main` at 668ef06 (after PR #27 was merged). We fixed the two items listed as remaining in the [acf8f0a](acf8f0a.md) review. For both, the test was written first and confirmed red before the fix (4 cases in `tests/security/pipe-swap.test.ts`; all 4 were red before the fix).

## Fixed

| # | Surface | What happened | How it was fixed | Test |
|---|---|---|---|---|
| 1 | Swapping the file | Whether the source is a regular file was checked only once, when opening, but the file is opened again for every query. If someone who can write to the root swapped the file for a FIFO after the check (or after opening), DuckDB hung at the open of the next query, and neither the clock's interrupt nor a disconnect reached it (on MCP HTTP it held a gate slot, and the process could not even exit). | When a query's clock runs out, or the caller goes away, in addition to the interrupt, if the source is a FIFO we open it on the writing side and close it (`releasePipe`). The waiting open finishes and fails to read as an empty pipe. The release on a clock timeout is repeated every 25 milliseconds until the query finishes, as for an abort (releasing once before the open cannot rescue an open that hangs later). The `CREATE VIEW` that binds the file at the start gets a 10-second clock through `watchOpen`, and when it runs out it releases in the same way and returns "did not open within". An engine that failed to open (a hung open, or a broken file) is closed after the read has finished (before, it was left unclosed). A query whose clock ran out is returned as "query stopped after N ms" even if the release produced a different error message. | 3 cases in `pipe-swap.test.ts` (the clock, a disconnect, `watchOpen`). Before the fix they did not return after waiting 4 seconds and were red. With `releasePipe` disabled, all 3 turn red (the `watchOpen` case also checks that the hung open itself finishes) |
| 2 | Web UI disconnects | Even when the connection dropped, that request's query kept running until the clock (10 seconds). The Web UI's engine has a single connection and operations run one at a time in order, so every later request had to wait. | The server creates an `AbortController` per request and aborts if the connection closes before the response has been written. `View` passes that signal to the engine for the duration of the operation (including the queries inside `fingerprint`, `checkPredicate` and `mintRefWith`). A call that went away while waiting its turn does not take a turn. The VS Code host also stops a running query when the editor is closed. `Engine.query` also accepts a per-query `signal`. | 1 case in `pipe-swap.test.ts` (0.7 seconds after the disconnect, the next request returns within 4 seconds. Before the fix it did not return even after 30 seconds and was red) |

## What remains

- **Swapping during opening**: a swap between the check and `CREATE VIEW` does not stay hung because `watchOpen` returns at 10 seconds, but the call waits during those 10 seconds. A test that creates the window during opening cannot be written deterministically, so we checked by applying `watchOpen` directly to a FIFO.
- **Queries without a clock**: an internal query that is passed no `timeoutMs` (such as `DROP TABLE`) is not stopped until the caller disconnects if it hits right after a swap to a FIFO. Every entry point that really runs has a clock or a signal.
- **Windows**: there are no FIFOs, and `releasePipe` does nothing.
