# Security review: e2399be

The target is `main` at e2399be (after PR #17 was merged). We fixed the three resource-usage items listed under "What remains" in [the 2f6dac7 review](2f6dac7.md). The fixes are in the same pull request. For every one, the test was written first and confirmed red before the fix.

## Found and fixed

| # | Surface | What happened | How it was fixed | Test |
|---|---|---|---|---|
| 1 | Weight of the card | `SUMMARIZE` in `fusen_card` and `fusen_peek` (and the CLI's card and the Web UI's card) had no clock. It reads every row of the file, so a large file holds the call until it finishes. | `buildCard` now has a clock (default 30 seconds, `CARD_TIMEOUT_MS`). When exceeded: "data card stopped after 30000 ms: the file is too large to summarize in time". It takes 0.14 seconds for 1 million rows and 0.8 seconds for 8 million, so ordinary files never reach it. | "building a data card is stopped by the clock" in `resources.test.ts` (before the fix it returned a card for 4 million rows, so it was red) |
| 2 | Disconnected requests | Even when the HTTP connection dropped, a running query did not stop until the 10-second clock arrived. | `openSource` now takes a `signal`, stops with `connection.interrupt()` when aborted, and refuses all later queries, and calls made during or before opening, with "the request was cancelled". DuckDB discards an interrupt aimed at a query that has not started (measured in independent review: the call right after missed 20 times out of 20), so after an abort the interrupt is repeated every 25 milliseconds until the query finishes. Each MCP tool passes the SDK's `extra.signal` (when the connection drops the transport closes and the SDK aborts this signal. Over stdio a cancellation notice does the same. HTTP is a separate server per request, so cancellation notices do not arrive, and what stops it is the disconnect). `signal` was also added to the opts of `mintRef`, `resolveRef` and `peek`. | 3 cases in `resources.test.ts` (before the fix: it ran the full 11.2 seconds, it opened even when already aborted, and resolve did not stop until the 10-second clock) |
| 3 | Number of concurrent calls | The HTTP server did not limit the number of simultaneous calls. Each call opens an engine (512MB of memory), so someone holding the token could use up memory by sending calls in parallel. | Tool calls go through a gate (`packages/mcp/src/gate.ts`). Up to 4 run at once, up to 16 wait in line, and beyond that it returns "the server is busy (…). Try again shortly.". A call whose connection drops while waiting leaves the queue. Requests that are not tool calls, such as `initialize`, are not limited. busy and cancelled are replies to the caller, so they are not written to standard error (the log does not overflow even when calls are sent in parallel). stdio has a single client, so it does not use the gate. | "queues work past the limit, …" in `mcp-http.test.ts` (with a limit of 1 and a queue of 1, the third is busy, and when the first is dropped the waiting card returns within 3 seconds. Before the fix the third got through, so it was red) |

Checked on the real thing: we started `fusen-mcp --http` in a separate process and sent 22 slow resolves at once, each running until the 10-second clock. RSS was 177MB, and the last 2 were refused as busy. A card right after dropping 20 connections returned in 33 milliseconds (both the running queries and the waiting calls had stopped).

## What we did not change

- The read-only protections (`allowed_paths`, external access banned, `temp_directory=''`, `lock_configuration`). All the existing cases of `pnpm test:security` are green.
- The canary tests are green in the form that goes through the gate too. The new error messages are fixed text and contain neither data values nor the token.
- The handling of prompt injection (the data block, fixed tool descriptions).

## What remains

- **PII masking**: policy A (detect by column name and by value shape, mask by default, and the only way to turn it off is the startup option `--unmask`), added in a following pull request. The mechanism and its limits are in ["Masking personal data" in docs/guide.md](../guide.md#masking-personal-data).
- **In exchange for stopping spilling**: a large `DISTINCT`, `GROUP BY` or `ORDER BY` does not spill and fails with Out of Memory. We keep the current form, on the safe side (see [2f6dac7](2f6dac7.md)).
- **Memory ceiling**: the gate limits the number of calls that run, not the number of open engines. A peek opens two engines in one call (card and resolve), and card, peek and resolve currently do not close the engine and leave it to GC (the change to close them comes in the harden pull request). So "4 × 512MB" is a guide for after that change goes in, and with peeks in parallel it can reach twice that.
- **The Web UI server**: it holds only one open file, and reading rows runs in order on that one connection, so we did not put this gate in. Sending `/api/open` in parallel can open files in parallel, but only a page holding the per-start token can send it. The card's clock applies to the Web UI too.
