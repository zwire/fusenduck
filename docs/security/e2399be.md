# セキュリティレビュー: e2399be

対象は `main` の e2399be(PR #17 のマージ後)です。[2f6dac7 のレビュー](2f6dac7.md)で「残っているもの」に挙げた資源の使い方の 3 件を直しました。修正は同じ pull request に入っています。どれもテストを先に書き、修正前に赤であることを確かめてから直しました。

## 見つけて直したもの

| # | 面 | 何が起きたか | 直し方 | テスト |
|---|---|---|---|---|
| 1 | card の重さ | `fusen_card`・`fusen_peek`(と CLI の card、Web UI のカード)の `SUMMARIZE` に時計がなかった。ファイルの全行を読むので、大きなファイルは終わるまで呼び出しを抱えたままになる。 | `buildCard` に時計をつけた(既定 30 秒、`CARD_TIMEOUT_MS`)。超えたら「data card stopped after 30000 ms: the file is too large to summarize in time」。100 万行で 0.14 秒、800 万行で 0.8 秒なので、普通のファイルには届かない。 | `resources.test.ts` の「building a data card is stopped by the clock」(修正前は 400 万行のカードを返して赤) |
| 2 | 切断された要求 | HTTP の接続が切れても、走っているクエリは 10 秒の時計が来るまで止まらなかった。 | `openSource` が `signal` を受け取り、中断されたら `connection.interrupt()` で止め、以後のクエリも開く前の呼び出しも「the request was cancelled」で断る。MCP の各ツールは SDK の `extra.signal` を渡す(接続が切れるとトランスポートが閉じ、SDK がこの signal を中断する。MCP の取り消し通知でも同じ)。`mintRef`・`resolveRef`・`peek` の opts にも `signal` を足した。 | `resources.test.ts` の 3 件(修正前は 11.2 秒走りきる、中断済みでも開く、resolve が 10 秒の時計まで止まらない) |
| 3 | 同時実行の数 | HTTP サーバーは同時に来た呼び出しの数を絞らなかった。呼び出しごとにエンジン(メモリ 512MB)を開くので、トークンを持つ相手は並べて送ればメモリを使い切れた。 | ツール呼び出しをゲートに通す(`packages/mcp/src/gate.ts`)。同時に 4 つまで走り(約 2GB が上限)、16 まで順番を待ち、それを超えたら「the server is busy (…). Try again shortly.」を返す。待っている間に接続が切れた呼び出しは列から抜ける。`initialize` などツール以外の要求は絞らない。stdio は 1 つのクライアントなのでゲートを使わない。 | `mcp-http.test.ts` の「queues work past the limit, …」(上限 1・待ち 1 で、3 本目が busy、1 本目を切ると待っていた card が 3 秒以内に返る。修正前は 3 本目が通って赤) |
