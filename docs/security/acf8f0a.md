# Security review: acf8f0a

The target is `main` at acf8f0a (after PR #24 was merged). This review covers what went in after [the e2399be review](e2399be.md): the Web UI (`apps/web`: the local server, the redeem code, the file list, columns and conditions, error display), the VS Code extension (`apps/vscode`), and the error display changed by harden #24. The fixes are in the same pull request. Attack cases were run against the real thing with throwaway scripts, and the ones we confirmed were kept in `tests/security`. For every fix, the test was written first and confirmed red before the fix.

PR #22 (.vsix), #23 (the feel of the Web UI) and #25 (PII masking) were not yet merged at this point, so we only read their diffs and wrote down what we noticed in the last section.

## What had no problem

- **The Web UI's entry**: it listens on only the three loopback addresses. `Host` and `Origin` other than the server's own three are 403 (DNS rebinding, requests from another page). The API is only `application/json` POSTs, so a page from another origin cannot make a simple request. `Origin: null` is also 403. The body is limited to 64KB.
- **Redeem code and token**: the code is 32 random bytes, goes in the URL fragment (not sent to the server), expires in 60 seconds, and cannot be used after one exchange. The token is another 32 bytes, normalized with sha256 and compared with `timingSafeEqual`. After the exchange the SPA removes the code from the URL with `history.replaceState`. That the code can be visible to other local users through the arguments of the command that opens the browser is as in ADR 0002, and if someone else uses it first the user's own page shows "already used", so they can notice.
- **File list**: symlinks are not followed, hidden files are skipped, and a folder swapped in is caught by `realpath` before and after reading. When opening, core checks the root again.
- **Columns and conditions**: a condition goes through `checkPredicate` (one simple SELECT) and the refusal of table-reading functions, `*` and `COLUMNS(*)`, and only then runs in the locked engine. Multiple statements, escapes through `UNION`, `--` comments and `LIMIT` give 400 (existing tests). A subquery that reads another file is refused by the engine and the page gets the withheld wording (new test). Column names are only the file's columns.
- **#24's error display**: only the first line of Parser/Binder/Catalog errors is shown. DuckDB writes candidates such as "Candidate bindings" on the second and later lines. We confirmed that using `read_csv` in a Ref's `where` to read the file's bytes as a CSV header makes the candidate names the file's bytes, but they are on the second line, so they are not shown. We also made struct keys, a failing cast, and a shape that reads as JSON into regression tests (5 cases in `errors.test.ts`, green even before the fix).
- **Secret leaks (canary)**: we put a canary in an environment variable and ran every Web UI API and four kinds of failure (outside the root, another file, `getenv`/`current_setting`, a failing cast). It appears in no response (new test). `getenv` does not exist in Node's DuckDB. The MCP canary is green in the existing tests.
- **Injection into the screen**: every cell is placed with `textContent`, and the CSP's `require-trusted-types-for 'script'` refuses `innerHTML`. Nothing runs for the e2e malicious cells (`<img onerror>`, `</script>`) (`pnpm test:e2e` 15 cases green).
- **VS Code extension**: the host opens only that editor's file, and only a string that passes `parseRef` can be put on the clipboard. The webview's CSP allows only scripts with a nonce, and `connect-src 'none'` means it can fetch nothing. There is no port and no token.
- **Read-only protection**: `allowed_paths`, external access banned, `temp_directory=''`, `lock_configuration`. All the existing cases of `pnpm test:security` are green.

## What remains

- **Swapping in a FIFO**: a gap remains between checking and DuckDB opening the file, in which the file could be swapped for a FIFO. Whoever can write to the root would have to swap the name right after the check. Closing it needs a mechanism where we open the file ourselves and hand it over, which DuckDB's Node API does not have.
- **Web UI disconnects and concurrency**: when a connection drops, the running query does not stop until the clock (10 seconds), and sending `/api/open` in parallel opens them in parallel. Both are things only a page holding the token can do, and as in [e2399be](e2399be.md) we have not put this in for now.
- **Names in binding errors**: on the first line, a file's column names or a struct's field names can appear as part of a type (`No function matches the given name and argument types '+(STRUCT("…" VARCHAR), INTEGER_LITERAL)'`). The names are strings from the file, but they are already visible in the card, and the line is cut at 300 characters. Whether to put wording for agents inside the data delimiters is a matter of a contract that changes the shape of errors, so it will be decided separately.
- **Column names in a Ref**: the names of selected columns go into the Ref's `cols=`, URL-encoded. A malicious column name also shows up in the Ref string an agent reads (the Ref's shape from before).

## What we noticed reading unmerged PRs

- **#25 (PII masking)**: masking applies to MCP and CLI output (rows and card), but not to the Web UI's and VS Code's row display (`View.rows`), while it does apply to the card's min/max. The person at the screen is whoever started it, so showing rows makes sense, but it would be good to write in the docs that the card and the rows are treated differently. Also, a Ref's `query`/`where` can use `read_text` to read the file's bytes as one string, so masking by column name does not apply (masking by value shape does). That is one example of what the PR says: "it slips through if a query changes the shape". Fix 2 above closed the route by which values leave through the logs without going through masking.
- **#22 (.vsix)**: with `untrustedWorkspaces.supported: true`, DuckDB parses a `.parquet` file even in a workspace in Restricted Mode. The engine's lock narrows what can be read and written, but does not protect against bugs in the parser itself. Opening is the user's action, so it is within what can be accepted, but setting it to `limited` so that it asks before opening in Restricted Mode is an option. When the DuckDB native module is fetched, it is checked against the integrity in `pnpm-lock.yaml`, which is fine.
- **#23 (the feel of the Web UI)**: the new wording is only the list of column names and the user's own condition string, and no values go in. Cells are also placed in a `title` attribute, but being an attribute it does not execute. No problem.
